## 1. One-Paragraph Problem Statement (User's Perspective)
Every attempt to launch (via .bat or ps1 -B -A -NC) gets the map/terrain visible in a custom 4p skirmish, but no starting units/infantry appear as selectable yellow-box sprites (or at all), with the session either "working" briefly or hard-crashing (0xC0000005 / exit after 30-60s visible runtime, crash zips captured). Vanilla-Plus profile exhibits the same "no units". Past "stable" deploys and experimental "visibility checkpoint" updates produced the same. DLLs pollute across profiles/live folders; launcher hygiene is unreliable (wrong profile picked by mtime auto-detect, -NC leaves state, no clean "restore vanilla", stray Scripts/RedAlert.dll). User has to "launch it" manually; nothing "just works". Stable-v1 itself documented "Invisible units" + "crashes after ~5min exemption" as known limitations. The project is not at a dev-resumable baseline.

## 2. Executive Summary of Root Cause (1-2 sentences)
The 3e53e4c "first non-crashing" guard commit (pinned for stable at outer 6cd627a..., sub .git/HEAD exactly 3e53e4cb31b9c5ac99c2c76aa76bb893bc7ff275) introduced Class_Is_Valid + Is_Plausible_Class_Pointer (OBJECT.H:304) early-outs in every Draw_It (INFANTRY.CPP:574, UNIT.CPP:2096, BUILDING.CPP:492, etc. via Is_Drawable template in OBJECT.H:340) + last-line +8 rejects in the two CC_Draw_Shape(ObjectClass*) overloads (CONQUER.CPP:3450 and :3487) that feed DLL_Draw_Intercept(...,16,16,...) on reject. Because starting player units (RTTI=28 infantry etc. created in CNC_Start_Custom_Instance for 4p maps) have garbage at +8 (0x80f8000 family, 0x00/0x80/0x81 high bytes) and/or shifted CCPtr<Class> layout during the narrow post-creation / first Map.Render() window (packing/ODR hazard under /Zp1 + WINDOWS_IGNORE_PACKING_MISMATCH + v145 toolset), Is_Drawable fails before any real CC_Draw_Shape / Techno_Draw_Object path, so Convert_Type (DLLInterface.cpp:4012) + population (DLLInterface.cpp:3464) never sees them with valid shape/asset/selectable data — only (at best) stub 16x16 feeds that don't produce drawable client sprites. The long exemption / 32x32 placeholders / HUMAN_EARLY / REAL_FIRST_REGISTRATION_FIX / grace were *only in later experimental submodule pointers* (e.g. 49228664..., 0fa1cdd1... "visibility checkpoint"); they were never in the 3e53e4c pin used for Stable baseline, so the "16x16 feed + long exemption" never existed together in the committed/deployed state that produced the "first non-crashing" milestone. Deployed DLLs today are polluted mixes (Stable dev ~1.250816M post-2026-06-07 build from pinned source; older Vanilla 1.256448M from May 17; some live sessions ran advanced experimental DLLs with the placeholder symbols despite source pin). This is why "map visible but no units + crash after 30-60s" and why vanilla also broken. (Specialist reports confirm: git 411 cites identical pins/dirty edit/stash; launcher audit cites exact ps1 lines 421/432 causing "newest Stable but final Vanilla" + 1270272 exp pollution into Stable, matching logs/sizes.)
